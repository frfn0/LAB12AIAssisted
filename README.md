Основная сущность предметной области — **книга** (`Item` в API, как требует

### Запуск


Интерактивная документация: <http://127.0.0.1:8000/docs>

### Эндпоинты

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/items` | список с поиском по названию/автору и пагинацией |
| POST | `/items` | создание книги |
| GET | `/items/{item_id}` | чтение книги |
| PUT | `/items/{item_id}` | частичное обновление |
| DELETE | `/items/{item_id}` | удаление книги |
| GET | `/items/stats/summary` | сводка по фонду |
| GET | `/health` | проверка состояния |

### Проверка


```
    HTTP 201
    {"isbn":"978-5-17-115205-5","title":"Мастер и Маргарита","author":"Булгаков М.А.",
     "year":1967,"genre":"Художественная литература","total_copies":3,"id":1,"available_copies":3}

3. POST /items - дубликат ISBN -> 409
    {"detail":"Книга с ISBN 978-5-17-115205-5 уже существует","error_type":"ConflictError"}

    {"detail":"Книга с id=999 не найдена","error_type":"NotFoundError"}
```

### Валидация и обработка ошибок

- схемы Pydantic v2 с аннотациями типов и ограничениями (`ge`, `le`,
  `min_length`, `max_length`), примеры значений для Swagger;
- доменные исключения `NotFoundError` (404), `ConflictError` (409),
  `BusinessRuleError` (409) приходят в ответе единым форматом
  `{"detail": ..., "error_type": ...}`;
- нарушение уникальности ISBN перехватывается обработчиком `IntegrityError`,
  поэтому конкурентные вставки тоже дают 409, а не 500;
- ограничения на уровне таблицы: `total_copies >= 0` и
  `0 <= available_copies <= total_copies`;
- бизнес-правила: нельзя уменьшить `total_copies` ниже числа выданных
  экземпляров; нельзя удалить книгу, у которой есть выдачи.

### Найденная и исправленная ошибка

Первая версия поиска работала неверно: запрос `search=булгаков` не находил
книгу с автором «Булгаков М.А.». Встроенная функция `lower()` в SQLite меняет
регистр только для символов ASCII:

```
SELECT 'Булгаков' LIKE 'булгаков'   ->  0
SELECT 'Abc'      LIKE 'abc'         ->  1
```

Исправление: в `app/database.py` на соединение SQLite регистрируется функция
`lower()` на Python, корректно работающая с Unicode. Конструкция `ilike()`
подхватывает её автоматически; в PostgreSQL, где `lower()` уже работает с
Unicode, вмешательство не требуется.

## Задание 3. Рефакторинг плохо написанного кода

Намеренно плохая функция расчёта штрафа за просрочку оставлена в
`app/services/fines_before.py`, рабочая версия — в `app/services/fines.py`.

### Проблемы исходной версии

1. длина функции больше 30 строк — 66 строк в одной функции;
2. магические числа — `1.50`, `30`, `1.5`, `500`, `5`, `0.9` без объяснения;
3. отсутствие обработки ошибок — неизвестная категория даёт `KeyError`,
   отсутствие поля `id` даёт `KeyError`, строка вместо даты даёт `AttributeError`;
4. неинформативные имена переменных — `l`, `k`, `d`, `dd`, `f`, `x`, `i`, `r`;
5. дублирование кода — фильтрация выдач читателя повторяется дважды,
   вычисление просрочки не вынесено в отдельную функцию.

### Объяснение каждого изменения

| Изменение | Зачем |
|-----------|-------|
| Одна функция 66 строк → шесть функций с одной ответственностью | Каждая функция делает одно и называется по делу: `overdue_days`, `loan_overdue_days`, `fine_for_loan`, `returned_on_time_count`, `discount_multiplier`, `summarize_reader_fine` |
| Магические числа → объект `FineRules` | Правила читаются из кода, а не угадываются; их можно переопределить без изменения логики |
| Добавлены `FineCalculationError`, `UnknownCategoryError` и проверки полей | Вместо `KeyError('vip')` приложение сообщает «Неизвестная категория читателя: 'vip'» |
| Имена `l`, `dd`, `f`, `x` → `loan`, `days`, `amount`, `on_time` | Код читается без возврата к формулировке задачи |
| Фильтрация выдач и подсчёт просрочки встречаются по одному разу | Устранено дублирование: счётчик возвратов вовремя вынесен в `returned_on_time_count` |
| Добавлен `FineSummary` со списком `LoanFine` | Клиент видит разбор по выдачам, а не только итоговое число |
| Деньги считаются через `Decimal` | Суммы не накапливают ошибку представления чисел с плавающей точкой |
| Режим округления сохранён (`ROUND_HALF_EVEN`) | При переходе на `ROUND_HALF_UP` сумма `104.625` стала бы `104.63` вместо `104.62` — рефакторинг не должен менять поведение |

#### Связи между таблицами

```
loans.book_id    -> books.id    (ON DELETE CASCADE)
loans.reader_id  -> readers.id  (ON DELETE CASCADE)
```

Связь один-ко-многим: одна книга может быть выдана много раз, один читатель
может иметь много выдач. При удалении книги или читателя все связанные
выдачи удаляются автоматически.

#### Индексы

| Индекс | Таблица | Поле | Зачем |
|--------|---------|------|-------|
| `ix_books_title` | books | title | Поиск по названию |
| `ix_books_author` | books | author | Поиск по автору |
| `ix_readers_full_name` | readers | full_name | Поиск читателя по имени |
| `ix_loans_issued_at` | loans | issued_at | Выдачи за период |
| `ix_loans_returned_at` | loans | returned_at | Поиск просроченных выдач |
| `ix_loans_book_id_reader_id` | loans | book_id, reader_id | Проверка, выдана ли книга читателю |

#### Ограничения

```
uq_books_isbn                   UNIQUE (isbn)
uq_readers_email                UNIQUE (email)
ck_books_total_copies_non_negative
    CHECK (total_copies >= 0)
ck_books_available_within_total
    CHECK (available_copies >= 0 AND available_copies <= total_copies)
```

В `Dockerfile` миграции применяются до запуска сервера, поэтому база всегда
готова к приёму запросов.

### Как устроена конфигурация

- `Dockerfile` копирует `requirements.txt` отдельным слоем и ставит
  зависимости до копирования кода: при изменении кода пересобирается только
  последний слой;
- `PYTHONDONTWRITEBYTECODE` и `PYTHONUNBUFFERED` убирают лишние файлы и
  делают логи видимыми сразу;
- `docker-compose.yml` поднимает `app` и `db`. Сервис `app` ждёт готовности
  PostgreSQL через `condition: service_healthy` и healthcheck `pg_isready`;
- данные PostgreSQL хранятся в именованном томе `pgdata` и переживают
  пересоздание контейнеров;
- `.dockerignore` исключает из образа тесты, результаты прогонов, локальный
  `.env` и файлы базы — в образе только `app`, `alembic`, `alembic.ini` и
  `requirements.txt`.

## Задание 5. Объяснение сложного кода

Разбираемый фрагмент: `app/services/fines.py` — расчёт штрафа за просрочку.

### Почему это сложный код

Здесь собраны четыре правила предметной области, которые влияют друг на друга:
ставка зависит от категории читателя, долгая просрочка умножается на
коэффициент, штраф ограничен сверху, а дисциплинированный читатель получает
скидку. Плюс нужно правильно определить, до какой даты считается просрочка.

### Объяснение простым языком

**1. Определяем дату отсчёта.**

Если книга не возвращена, просрочка считается на сегодняшний день — она растёт
каждый день. Если книга возвращена, отсчёт останавливается на дате возврата:
после возврата штраф перестаёт расти.

**2. Считаем дни просрочки.**

Вычитаем из даты отсчёта дату, до которой книгу нужно было вернуть. Если
результат отрицательный (книгу вернули раньше срока), просрочки нет.

**3. Считаем штраф по одной выдаче.**

Базовая формула: дни просрочки × ставка 1.50 руб. в день. Ставка зависит от
категории: студент — как есть, обычный читатель — ×1.5, сотрудник — ×0.5.

Если просрочка длиннее 30 дней, штраф умножается на 1.5. Штраф по одной
выдаче не может превышать 500 руб.

**4. Считаем скидку за дисциплинированность.**

Если читатель возвращал книги вовремя пять и более раз, итоговый штраф
умножается на 0.9 — скидка 10%.

**5. Складываем и округляем.**

Сумма по всем просроченным выдачам умножается на коэффициент скидки и
округляется до копеек. Округление — банковское (`ROUND_HALF_EVEN`):
`104.625` → `104.62`, а не `104.63`.

### Пример

Читатель-студент задержал три книги:

| Книга | Просрочка | Расчёт | Штраф |
|-------|-----------|--------|-------|
| А | 2 дня | 2 × 1.50 | 3.00 |
| Б | 30 дней | 30 × 1.50 | 45.00 |
| В | 31 день | 31 × 1.50 × 1.5 | 69.75 |

Итого до скидки: 117.75 руб. При пяти возвратах вовремя: 117.75 × 0.9 = 105.98 руб.

### Предложенные улучшения

| Улучшение | Зачем |
|-----------|-------|
| Перенести правила в конфигурацию | Библиотекарь может изменить ставку без пересборки |
| Добавить тесты на граничные значения скидки | Зафиксировать границу: 4 возврата — без скидки, 5 — со скидкой |
| Добавить логирование расчёта | Объяснить читателю, откуда взялась сумма |
| Рассмотреть частичное погашение штрафа | Читатель может оплатить часть, остаток пересчитывается |
| Вынести ставки в таблицу базы | История изменений ставок, какая ставка действовала на момент выдачи |

### Что уже сделано

- правила вынесены в `FineRules` и могут быть переопределены при вызове;
- тесты на границу скидки: 4 возврата без скидки, 5 возвратов со скидкой;
- разбор по выдачам (`FineSummary`) показывает, из чего складывается итог.

### Что сознательно не делалось

- логирование расчёта — для лабораторной работы избыточно;
- частичное погашение — отдельная бизнес-задача, требует сущности «платежи»;
- вынос ставок в базу — преждевременная оптимизация для текущего объёма правил.

## Задание 8. Поиск уязвимостей в коде

Код проверен по всем пунктам, перечисленным в задании: SQL-инъекции, XSS,
незащищённые эндпоинты, отсутствие валидации входных данных и незакрытые
соединения. Проверки выполнены вживую против работающего приложения, а не
только просмотром кода.

### Отчёт: что нашёл → в чём проблема → как исправил

| Что сгенерировал ИИ | В чём проблема | Как исправил |
|---------------------|----------------|--------------|
| Ответ 422 от Pydantic со стандартным телом | В каждой ошибке повторяются входные значения (`input`, `ctx`). Если в запрос попадёт пароль или персональные данные, они вернутся клиенту и останутся в логах | Добавлен обработчик `RequestValidationError`, который отправляет только `type`, `loc`, `msg` |
| Отсутствие обработчика необработанных исключений | FastAPI отдаёт текст исключения. Ошибка вида `sqlite://user:secret@host/db` раскрывает строку подключения, имена таблиц и столбцов | Добавлен обработчик `Exception`: клиенту уходит «Внутренняя ошибка сервера», детали — только в лог |
| Никаких защитных заголовков | uvicorn их не выставляет. Без `X-Content-Type-Options` браузер может угадать MIME-тип ответа, без `X-Frame-Options` страницу можно встроить в iframe | Добавлен `SecurityHeadersMiddleware` с набором заголовков, применяется и к ошибочным ответам |
| `response.headers.pop("server", None)` | Код выглядел правильно, но не работал: uvicorn добавляет заголовок `Server` на уровне транспорта уже после возврата ответа. Тест проходил, потому что `TestClient` так не делает | Удалён мёртвый код, добавлен флаг запуска `--no-server-header` в `Dockerfile` и инструкции |
| Масс-присваивание: `ItemCreate` без `extra="forbid"` | Лишние поля молча игнорировались. Клиент, приславший опечатку в поле или попытку подменить `id`, получал `201` и не знал об этом | В `ItemBase` добавлен `model_config = ConfigDict(extra="forbid")`, лишние поля дают `422 extra_forbidden` |
| Открытые эндпоинты изменения данных | Любой, кто знает адрес, мог создавать, изменять и удалять книги | Добавлена проверка заголовка `X-API-Key` на `POST`, `PUT`, `DELETE`. Чтение осталось открытым |
| Сравнение ключа через `==` | Обычное сравнение завершается на первом несовпадении, и по времени ответа ключ можно подбирать посимвольно | Используется `secrets.compare_digest` — сравнение постоянного времени |
| Поиск через `ilike(f"%{search}%")` без экранирования | SQLAlchemy параметризует значение, поэтому инъекция не проходит. Но спецсимволы `%` и `_` внутри запроса работали как маски: `search=%` возвращал весь каталог | Добавлена функция `_escape_like`, экранирование символа-разделителя первым, и `escape=LIKE_ESCAPE` в запросе |

| Проверка | Результат |
|---|---|
| SQL-инъекция `' OR 1=1--` | Не сработала, SQLAlchemy параметризует запросы |

### Отчёт 1. Топ-10 книг по числу выдач за последний месяц

*Какие книги выдавались чаще всего за последний месяц, сколько разных
читателей их брало и какой средний штраф сопровождает выдачу?*

```sql
SELECT
    b.title,
    b.author,
    b.genre,
    COUNT(l.id)                  AS issues_count,
    COUNT(DISTINCT l.reader_id)  AS readers_count,
    ROUND(CAST(AVG(l.fine) AS NUMERIC), 2) AS avg_fine
FROM loans l
JOIN books b ON b.id = l.book_id
WHERE l.issued_at >= :since
GROUP BY b.id, b.title, b.author, b.genre
ORDER BY issues_count DESC, b.title
LIMIT 10
```

```
title                  | author        | issues_count | readers_count | avg_fine
-----------------------+---------------+--------------+---------------+---------
English Grammar in Use | Свободный Т.  | 3            | 3             | 9.00
Дюна                   | Герберт Ф.    | 3            | 3             | 4.00
Мастер и Маргарита     | Булгаков М.А. | 3            | 3             | 10.00
Clean Code             | Мартин Р.     | 2            | 2             | 15.75
Анна Каренина          | Толстой Л.Н.  | 1            | 1             | 0.00
```

**Логика:** `JOIN` соединяет выдачу с книгой; `WHERE` отсекает выдачи старше
месяца; `COUNT(l.id)` даёт число выдач, а `COUNT(DISTINCT l.reader_id)` —
число разных читателей (это разные вещи: пять выдач одному человеку — это
пять выдач и один читатель); `GROUP BY` собирает строки по книге; в
`ORDER BY` добавлена сортировка по названию при равенстве, чтобы результат
был воспроизводимым.

### Отчёт 2. Читатели с максимальной суммой штрафов

*Кто из читателей больше всего должен библиотеке и у скольких книг
находятся сейчас?*

```sql
SELECT
    r.full_name,
    r.email,
    COUNT(l.id)                                           AS loans_total,
    SUM(CASE WHEN l.returned_at IS NULL THEN 1 ELSE 0 END) AS active_loans,
    ROUND(CAST(SUM(l.fine) AS NUMERIC), 2)                 AS total_fine,
    ROUND(CAST(AVG(l.fine) AS NUMERIC), 2)                 AS avg_fine
FROM readers r
JOIN loans l ON l.reader_id = r.id
GROUP BY r.id, r.full_name, r.email
HAVING SUM(l.fine) > 0
ORDER BY total_fine DESC
LIMIT 10
```

```
full_name       | loans_total | active_loans | total_fine | avg_fine
----------------+-------------+--------------+------------+---------
Петрова Анна    | 4           | 1            | 42.00      | 10.50
Сидоров Пётр    | 4           | 1            | 28.50      | 7.13
Иванов Иван     | 3           | 2            | 24.00      | 8.00
Кузнецова Мария | 3           | 0            | 21.00      | 7.00
```

**Логика:** `CASE` превращает проверку «книга сейчас выдана» в 1 или 0, чтобы
посчитать такие выдачи через `SUM`. Фильтр стоит в `HAVING`, а не в
`WHERE`: `WHERE` отсёк бы строки до группировки и сломал бы суммы.

### Отчёт 3. Книги, которые чаще всего возвращают с просрочкой

*Какие книги чаще остаются у читателей дольше срока и какой процент
возвратов это составляет?*

```
title                  | returns_total | overdue_returns | overdue_rate
-----------------------+---------------+-----------------+------------
Анна Каренина          | 2             | 1               | 50.0
Мастер и Маргарита     | 3             | 0               | 0.0
Дюна                   | 2             | 0               | 0.0
English Grammar in Use | 2             | 0               | 0.0
```

**Логика:** `WHERE returned_at IS NOT NULL` отсекает невозвращённые книги —
для них просрочка ещё растёт и процент считать бессмысленно. `100.0` перед
делением превращает долю в проценты: без него деление было бы целочисленным.
`HAVING COUNT(l.id) >= 2` убирает книги с единственным возвратом, где
процент недостоверен. Полный текст запроса — в
[scripts/demo_task9.py](scripts/demo_task9.py).

### Отчёт 4. Популярность жанров и средняя нагрузка на книгу

*Какие жанры читают чаще и сколько выдач приходится на одну книгу в жанре?*

```
genre                     | issues_count | titles_count | issues_per_title
--------------------------+--------------+---------------+-----------------
Художественная литература | 6            | 2             | 3.00
Учебники                  | 3            | 1             | 3.00
Фантастика                | 3            | 1             | 3.00
Программирование          | 2            | 1             | 2.00
```

**Логика:** сравниваются не только абсолютные числа, но и удельные. Жанр с 50

```
ERROR:  function round(double precision, integer) does not exist
```

В PostgreSQL `round()` определена только для `numeric`, а `AVG()` по колонке
типа `double precision` возвращает `double precision`. SQLite такой вызов
принимает молча, поэтому ошибка проявилась только при проверке на второй
базе — а именно ради такой проверки и выполнялась этапом.

Исправлено приведением к `numeric`: `ROUND(CAST(AVG(l.fine) AS NUMERIC), 2)`.
Отчёты 3 и 4 работали без `CAST`, потому что деление там выполняется на
`100.0` и `1.0`, что приводит результат к `numeric` само по себе.

### Про порог по дате

Порог отчётного периода передаётся параметром `:since`, а не вычисляется
функцией базы: в SQLite это `date('now', '-30 days')`, в PostgreSQL —
`NOW() - INTERVAL '30 days'`. Два разных текста запроса означали бы риск
расхождения между средами.

## Задание 10. Генерация регулярного выражения

Задача валидации: ISBN книги библиотечного фонда. Принимается ISBN-10 или
ISBN-13, дефисы и пробелы допускаются.

### Регулярные выражения

**ISBN-10**

```
^(?:\d{1,5}-(?:\d{1,7}-)?(?:\d{1,6}-)?[\dX]|\d{9}[\dX])$
```

| Часть | Значение |
|-------|----------|
| `\d{1,5}` | первая группа произвольной длины от 1 до 5 цифр |
| `(?:\d{1,7}-)?` | вторая группа, необязательная |
| `(?:\d{1,6}-)?` | третья группа, необязательная |
| `[\dX]` | контрольная цифра: цифра либо X (римская десятка) |
| `\d{9}[\dX]` | альтернатива для записи без дефисов |

**ISBN-13**

```
^(?:978|979)(?:-?\d){10}$
```

| Часть | Значение |
|-------|----------|
| `(?:978\|979)` | книжный префикс, обязателен |
| `(?:-?\d){10}` | десять цифр, перед каждой дефис допускается |

### Почему одного регулярного выражения недостаточно

```
значение               регулярное    полная     примечание
978-5-17-115205-6      да            нет        верная форма, неверная контрольная цифра
0804429571             да            нет        неверная контрольная цифра ISBN-10
978517115205           нет           нет        только двенадцать цифр
9775171152055          нет           нет        ISBN-13 не может начинаться с 977
abc-def-ghij           нет           нет        буквы вместо цифр
```

Строка `978-5-17-115205-6` проходит проверку шаблоном, но отвергается полной
проверкой: форма верная, контрольная сумма не сходится. Если бы в схеме
стоял только `Field(pattern=ISBN13_REGEX)`, в базу попадали бы номера с
опечатками в контрольной цифре.

Полная проверка состоит из двух шагов: регулярное выражение для формы и
арифметика для контрольной суммы.

**ISBN-10, модуль 11:** сумма цифр с весами 10, 9, …, 2 должна делиться на
11; остаток 1 означает контрольную цифру X.

**ISBN-13, модуль 10 с чередованием весов:** сумма первых двенадцати цифр с
весами 1, 3, 1, 3, …; контрольная цифра = `(10 - остаток) mod 10`.

### Как получены корректные номера

Номера построены функциями, а не выписаны вручную:

```python
make_isbn13("978517115205")   # -> 9785171152055
make_isbn10("080442957")     # -> 080442957X
```

Это не мелочь: при первой попытке почти все номера были выписаны вручную и
оказались неверными. Именно подключение настоящей проверки к схеме из задания
1 это выявило — тестовые данные перестали проходить валидацию.

### Интеграция в приложение

Поле `isbn` в схеме проверяется полностью и нормализуется: дефисы и пробелы
убираются, поэтому `978-5-17-115205-5` и `9785171152055` сохраняются
